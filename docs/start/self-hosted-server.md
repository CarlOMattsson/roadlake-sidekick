Start Sidekick on your own Linux server with Docker Compose. The guide goes from a fresh clone to a server that answers, in the order you need the steps.

## Requirements

- Linux x86_64 with Docker Engine and the Docker Compose plugin (v2.24 or newer, see `docker compose version`), and
  `git`, `openssl`, `curl`. For updates to a signed image later: `cosign` and `python3` (3.9 or newer).
- Either a public domain whose DNS points at the machine, with ports 80 and 443 reachable (`vps` profile: Caddy
  obtains the certificate), or a tunnel that forwards HTTPS to `127.0.0.1:8000` (home machine). Claude reaches the
  server from Anthropic's cloud, so the address must be public HTTPS in both cases.
- A GitHub account for the sign-in (you create the OAuth app yourself, see [Connect Claude](../operate/connect-claude.md)).
- Secrets generated by you. Nothing secret lives in this repository.

There is no published image yet: the first start builds the API image from this checkout (a few minutes). Updating
to a signed, digest-pinned image is described under [Update](../operate/update.md).

## First start

Get the code, then run everything from `deploy/selfhost`, as a user that may run `docker`:

```bash
git clone https://github.com/CarlOMattsson/roadlake-sidekick.git
cd roadlake-sidekick/deploy/selfhost
```

**1. Copy the configuration and generate the secrets.**

```bash
cp selfhost.env.example selfhost.env && chmod 600 selfhost.env
cp db.env.example db.env && chmod 600 db.env
cp Caddyfile.example Caddyfile            # vps profile only

openssl rand -base64 48   # one value each: SIDEKICK_CURSOR_SIGNING_SECRET, SIDEKICK_TOKEN_PEPPER, SIDEKICK_MCP_OAUTH_SIGNING_KEY
openssl rand -hex 32      # hex only for the database passwords (they sit inside URLs): POSTGRES_PASSWORD, SIDEKICK_DB_APP_PASSWORD, SIDEKICK_DB_MIGRATOR_PASSWORD
```

Edit both files and replace every `replace-with-` value. The app password also goes into
`SIDEKICK_DATABASE_URL` (`selfhost.env`) and the migrator password into `SIDEKICK_MIGRATION_DATABASE_URL` (`db.env`).
Use your public host name (on a home machine, the tunnel's) as `SELFHOST_DOMAIN=sidekick.example.com`, and the full
HTTPS origin as `SIDEKICK_MCP_PUBLIC_BASE_URL=https://sidekick.example.com`, without a trailing slash.
PostgreSQL creates its roles from `db.env` only on the first start of an empty volume, so choose the passwords before
the first start. Leave the GitHub client id, the client secret and the identity line as they are for now: steps 3 and 4
fill them in.

*Choose the language.* Set `SIDEKICK_MCP_APP_LOCALE=sv` (Swedish, the default) or `en` (English) in `selfhost.env`
(uncomment the line). It sets the language of the apps and of Claude's answers. If an AI assistant sets this up for you,
it must ask you which language you want (proposing Swedish) and which rooms (`SIDEKICK_ENABLED_ROOMS`; proposing all
rooms) and must not continue without your answers.

**2. Build the image.** The two variables let the app count how old its code is for the
update reminder; they are optional.

```bash
export SIDEKICK_BUILD_COMMIT="$(git log -1 --format=%h)" SIDEKICK_BUILD_DATE="$(git log -1 --format=%cI)"
docker compose --env-file selfhost.env build
```

**3. Create the owner and get its id.** `sidekick-admin create-user` creates the one user that your sign-in will map
to. It needs no password and no terminal, and it does not check the OAuth settings (a user has to exist before the
identity line can name it). It starts PostgreSQL, runs the migrator and prints the new user's UUID, the only line on
standard output:

```bash
docker compose --env-file selfhost.env run --rm -T api sidekick-admin create-user --login owner --display-name "Owner"
```

Write the UUID down. Your numeric GitHub id (not the login) is the `id` field of
`curl -s https://api.github.com/users/<your-github-login>`.

**4. Create the GitHub OAuth app and fill in the identity.** Do the first part of [Connect Claude](../operate/connect-claude.md) now
(register the app, copy its client id and secret into `selfhost.env`). Then set the identity line to your GitHub id and
the UUID from step 3, and check that no placeholder is left (this must print nothing):

```text
SIDEKICK_MCP_OAUTH_ALLOWED_IDENTITIES=github:<numeric GitHub id>=<UUID from step 3>
```

```bash
grep -nE '^[A-Z_]+=.*replace-with-' selfhost.env db.env
```

Optional but recommended: keep the Sidekick secrets out of the containers' environment variables by moving them into files with `sh secrets-to-files.sh` (see [Secrets as files](../operate/limits-and-secrets.md#secrets-as-files)). Run it after the check above; it leaves a secret that still says `replace-with-` where it is.

**5. Start.**

```bash
docker compose --env-file selfhost.env --profile vps up -d    # VPS with Caddy and automatic TLS
docker compose --env-file selfhost.env up -d                  # home machine behind a tunnel
```

Optional profiles can be added to the same command line: `--profile memory` ([Memory](../operate/memory.md)),
`--profile backup`, `--profile push` (uses `ntfy.env`; one-time setup with `sh ntfy-init.sh`; own ntfy needs the `vps`
profile). The header of `compose.yaml` shows each command. Only Caddy (or your tunnel) is public. The API listens on
`127.0.0.1:8000` only. PostgreSQL has no route to the internet; the API, the push and memory workers and Hindsight sit
on a network that does (for GitHub, ntfy and your model provider).

Caddy's access log (stdout, rotated like every container log) holds the time, status, method, host, duration, size,
a request id and a fixed route class (`mcp`, `oauth`, `well-known`, `companion`, `push` or `unmatched`). It never
holds the URL path, the query string, headers, the client address or a body: `/mcp/anything` is logged as `mcp`.
The error line of a failed proxy attempt is stripped of its request in the same way.

The base stack also starts `automation-worker` (no profile needed): it runs scheduled processes, turning each due
process run into tasks every 30 seconds. Without it a scheduled process never runs. It reaches PostgreSQL only (no
published port, no route to the internet) and needs no settings of its own. `update.sh` stops and restarts it with the API.

**6. Check.** The API answers its health check when it is up (`docker compose --env-file selfhost.env ps` shows
`healthy`). On the machine itself, before DNS or the tunnel exist, check it like this:

```bash
curl -s http://127.0.0.1:8000/.well-known/oauth-protected-resource/mcp          # 200 and a JSON document
docker compose --env-file selfhost.env exec -T api python -m sidekick.shared.readiness   # prints "ok"
```

`/health/live` and `/health/ready` are not served by this stack: from outside, and also on `127.0.0.1:8000`, they answer
404 on purpose, because the public surface is an allowlist. They exist only in the local developer setup
([QUICKSTART.md](../../QUICKSTART.md)). The container's own health check uses the `readiness` module above. Once the
public address works, the same discovery document is served there:

```bash
curl -s https://<your-domain>/.well-known/oauth-protected-resource/mcp
```

If the api container keeps restarting, `docker compose --env-file selfhost.env logs api` names the setting it refuses
(`undeclared SIDEKICK_ setting`, a missing OAuth value, a placeholder secret).

**If the first start failed.** PostgreSQL creates its roles only on the first start of an empty volume, and a volume
left half initialised skips that step on every later start. Fix the cause, then remove the volume before trying again
(this deletes the database, so only on a first start that never worked):
`docker compose --env-file selfhost.env down -v`.

**Strict umask.** A restrictive umask (`077`, common on hardened servers) makes every file in a fresh checkout
readable by you only. The compose file and the image copy what the containers need as root, so the database roles and
the code work either way. The one file a container reads straight from the checkout is `ntfy/server.yml` (own ntfy,
`push` profile); `sh ntfy-init.sh` makes it world-readable, since it holds no secret. To check:

```bash
ls -l ntfy/server.yml     # the mode must show "r" for group and others, for example -rw-r--r--
```

Secret files (`selfhost.env`, `db.env`, `ntfy.env`) stay mode 600 on purpose.
